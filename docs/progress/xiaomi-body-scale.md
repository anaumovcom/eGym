# Xiaomi Mi Body Composition Scale 2 (XMTZC05HM)

## Архитектура

Функция работает внутри существующего FastAPI backend, без отдельного процесса,
MQTT, Xiaomi-приложения, облака, GATT-соединения или ручного сопряжения.
По умолчанию на новой установке поиск **включён автоматически** вне упражнения.
Ранее сохранённое ручное выключение сохраняется. При настройке/выполнении
упражнения, отдыхе между подходами и калибровке реальное BLE-сканирование
приостанавливается без изменения настройки включения и возобновляется после выхода.

- `ScaleService` запускается и останавливается через lifespan приложения.
  Bleak и обработка пакетов работают асинхронно; короткие SQLAlchemy-транзакции
  выполняются через `asyncio.to_thread`. Очередь пакетов ограничена 64 записями,
  обнаруженных устройств — 32, очередь каждого WebSocket-подписчика — одним сигналом.
- Настройки `ble_body_scale` хранятся в существующей таблице `app_settings`.
  Выбираются **конкретные общие весы**. Каждый новый стабильный замер записывается
  пользователю с `is_current=true` в момент сохранения. Старые настройки привязки
  профиля игнорируются; повторная привязка при смене пользователя не требуется.
- Вес и UTC-время приёма сохраняются в существующую `body_measurements`.
  `scale_readings` содержит идентификатор устройства, ключ дедупликации и импеданс.
  Все записи и `UserProfile.weight_kg` обновляются одной транзакцией.
  Существующая аналитика и история профиля получают новый вес автоматически.
- Отдельная подписка `/api/scales/realtime` повторяет архитектурный паттерн
  hardware WebSocket, но не смешивает BLE с моторной телеметрией или командами.
  Frontend использует React Query, переподключение WebSocket и REST fallback.
- Интерфейс: **Прогресс → Тело → Вес тела**. История и график за 7/30/90 дней.
  Панель доступна даже при ошибке основной загрузки прогресса.
- Глобальный `ScaleRealtimeProvider` показывает «Вес сохранён» и проигрывает
  `/audio/success.mp3` через существующий менеджер звуков, учитывая настройки
  громкости и приоритет голоса тренера. Старые данные, обновления импеданса,
  heartbeat и удаление не вызывают повторных сигналов. Ограничения autoplay
  браузера могут требовать предварительного касания экрана.
- История допускает удаление с подтверждением. Удаляются измерение и BLE-provenance,
  профиль восстанавливает предыдущий вес, если удалён его последний замер.
  Ограниченный журнал 256 удалённых ключей препятствует немедленному возврату
  удалённого замера из повторных рекламных пакетов.
- Автопауза использует `/api/scales/activity`: heartbeat каждые 5 секунд,
  lease 20 секунд, монотонная sequence от каждой вкладки, до 64 клиентов.
  Любая активная вкладка с setup/exercise/rest удерживает паузу. Backend также
  раз в 250 мс читает под lock активность workout/calibration без команд или I/O.
  Пакеты во время паузы и накопленные до перехода отбрасываются.

Контур управления двигателем, рабочие нагрузки, калибровки, защитные ограничения
и настройки тренера не изменяются. Масса в профиле уже используется для оценок
энергозатрат, но не для расчёта моторного усилия. Остальные модули могут читать
последний вес через API или `ScaleRepository.latest`; автоматическая персонализация
рабочих нагрузок намеренно не реализована.

## Проверенный формат BLE

Источники, изученные при реализации:

- [ESPHome xiaomi_miscale](https://github.com/esphome/esphome/blob/dev/esphome/components/xiaomi_miscale/xiaomi_miscale.cpp).
- [Python BLE Monitor miscale](https://github.com/custom-components/ble_monitor/blob/master/custom_components/ble_monitor/ble_parser/miscale.py).
- [Python xiaomi_mi_scale / Bleak](https://github.com/lolouk44/xiaomi_mi_scale/blob/master/src/Xiaomi_Scale.py).
- [Bleak Linux backend](https://bleak.readthedocs.io/en/latest/backends/linux.html).

Service data UUID `0000181b-0000-1000-8000-00805f9b34fb`: ровно 13 байт,
**без** заголовка AD и двух байт UUID.

| Байты | Значение |
|---|---|
| 0 | Единицы: `0x02` kg, `0x03` lb |
| 1 | bit 1: импеданс доступен; bit 5: стабилизация; bit 6: jin; bit 7: нагрузка снята |
| 2–3 | Год, unsigned little-endian |
| 4–8 | Месяц, день, часы, минуты, секунды |
| 9–10 | Импеданс, unsigned little-endian |
| 11–12 | Вес, unsigned little-endian |

Преобразования: kg = raw / 200; lb = raw / 100 × 0.45359237;
jin = raw / 100 × 0.5 (приоритет bit 6 второго байта).
Промежуточный вес не сохраняется. Пакеты снятия нагрузки только переоткрывают
цикл измерения. Некорректный импеданс не мешает сохранить достоверный вес;
поздний импеданс дополняет существующее измерение, не создавая новую запись.

Дедупликация: один результат на цикл нагрузки, затем переоткрытие по снятию
нагрузки, новой нестабильной фазе или паузе более 120 секунд. Частые повторные
стабильные пакеты сами по себе цикл не переоткрывают. Дополнительно БД хранит
уникальный ключ device + clock + weight; при несинхронизированных часах
используется защита от одинакового веса (допуск 0.1 kg) за 120 секунд.
Время весов не считается достоверным временем измерения: используется UTC backend.

## Linux / Bluetooth

Зависимость `bleak>=1.1,<3.0` включена в backend dependencies.
Нужны работающие BlueZ, системная D-Bus, включённый BLE-адаптер и доступ
пользователя backend к адаптеру. Не следует запускать всё приложение от root.
В контейнере потребуются проброс системной D-Bus и соответствующие права.

Первым пробуется настоящий пассивный режим BlueZ с AdvertisementMonitor:
AD type `0x16`, offset 0, UUID bytes `1b18`. При отсутствии поддержки
пассивного режима выполняется fallback на активное сканирование advertising,
с видимым предупреждением. Сопряжение и GATT по-прежнему не используются.
Другие ошибки не запускают бесконечные немедленные повторы: повтор через 10 секунд.
Регистрация сканера обновляется каждые 15 секунд для выявления отключённого адаптера.

На текущем компьютере проверено: адаптер BlueZ доступен, пассивный режим требует
BlueZ >= 5.56 / experimental и kernel >= 5.10; fallback успешно запустил активный
BLE-поиск. Настройки включения и выбора весов при этой smoke-проверке не менялись.
Параметры BlueZ автоматически не изменяются.

## Проверка на реальных весах

1. Установить обновлённые backend dependencies обычным способом проекта.
   Применить миграцию `20261018_0013` штатной процедурой Alembic. В local-режиме
   новый additive table также создаёт существующий bootstrap `create_all`.
2. Открыть приложение и нужный профиль, затем **Прогресс → Тело**.
3. Поиск запускается автоматически (или нажать **Включить поиск**, если он
  ранее выключен вручную). При недоступном Bluetooth должна появиться ошибка,
   но приложение и тренировки должны оставаться работоспособны.
4. Разбудить весы, встав на них рядом с компьютером. Найти `MIBCS` или другое
   имя вместе с адресом; при нескольких устройствах выбрать нужный адрес.
5. Нажать **Выбрать весы**. Проверить адрес и текущий активный профиль.
   Первое взвешивание до выбора устройства намеренно не записывается.
6. Сойти и взвеситься повторно. При колебании веса виден процесс измерения;
   после стабилизации появляются вес, время и ровно одна строка истории.
7. Оставаться на весах и дождаться импеданса: новая строка появляться не должна.
   Сравнить kg со значением дисплея. При возможности повторить в lb/jin.
8. Проверить 7/30/90 дней; открыть профиль — новый вес доступен в обычной истории.
9. Перезапустить backend штатно в безопасном состоянии тренажёра: выбранные
  весы, включение поиска и история должны сохраниться.
10. В безопасном состоянии тренажёра выключить Bluetooth, убедиться в ошибке
    поиска, включить обратно: поиск восстановится автоматически, обычно за
    15–30 секунд. Постоянный статус «подключено» весам не показывается.
11. Переключить активный профиль и взвеситься заново: новый замер должен попасть
  выбранному пользователю без перенастройки весов.
12. Проверить уведомление и звук при новом результате. Обновить страницу:
  старый результат не должен повторно сопровождаться звуком.
13. Удалить ошибочный замер через корзину и подтверждение. Проверить график,
  профиль и отсутствие немедленного возврата удалённой строки.
14. Перейти к настройке/выполнению упражнения: поиск должен остановиться;
  выйти в прогресс/главную: поиск должен восстановиться, если включён.

## API

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/scales/status` | Настройки, Bluetooth, поиск, процесс измерения, устройства |
| PUT | `/api/scales/settings` | `{enabled, deviceId}`; устройство должно быть обнаружено |
| PUT | `/api/scales/activity` | `{clientId, sequence, phase}`; временная автопауза |
| DELETE | `/api/scales/measurements/{id}?userId=…&confirm=true` | Удалить замер указанного владельца |
| POST | `/api/scales/scan/start` | Включить и сохранить автопоиск |
| POST | `/api/scales/scan/stop` | Выключить и сохранить настройку |
| GET | `/api/scales/measurements/latest?userId=…` | Последний BLE-вес независимо от периода |
| GET | `/api/scales/measurements?userId=…&days=30` | История BLE-измерений, до 500 строк |
| WS | `/api/scales/realtime` | Начальный статус, обновления и heartbeat |

Публичного API ввода произвольного BLE-измерения нет. Ручные измерения по-прежнему
доступны через существующий интерфейс профиля. История профиля объединяет ручные
и автоматические измерения; отдельный график весов показывает только BLE.

## Автотесты и ограничения

Backend: `test_scale_protocol.py` и `test_scales.py`; frontend:
`body-weight-panel.test.tsx`. Файл `fixtures/scale_advertisements.json` содержит
синтетическую последовательность сырых service data, построенную по проверенному
формату. Replay-тест принимает hex-пакеты без физического Bluetooth. Реально
записанные service data можно подставлять в том же формате; fixture не выдаётся
за запись с физических весов.

- После обновления: 87 backend-регрессионных тестов и 92 выбранных frontend-теста
  (весы, прогресс, звуки, Router/Providers; backend также hardware/runtime/тренер).
- Ruff нового backend-кода проходит. Полная TypeScript-проверка блокируется
  существующими ошибками фото, моков и других экранов, не связанными с весами.
- При проверке обновления получен live BLE-замер 83.8 кг от `MIBFS`, сохранён
  активному Алексею и показан в интерфейсе вместе с уведомлением. Физическая
  точность относительно дисплея и воспроизведение звука на динамиках требуют
  подтверждения пользователем. Реальная остановка сканера по setup lease проверена.
- Поддержан рекламный протокол Mi Scale V2 `181B`, не любые устройства с таким
  UUID. Рекламные пакеты не аутентифицированы, имя/адрес не доказывают модель.
- Поддерживаются одни общие выбранные весы на установку. Автораспознавания человека
  по весу нет: перед взвешиванием нужно выбрать активный профиль. BLE должен
  обслуживать один backend worker, как и hardware runtime.
- Валидный, но застывший clock весов может подавлять последующие измерения того же
  веса; без валидного clock одинаковые взвешивания за две минуты объединяются.
  После долгой паузы и перезапуска невозможно безусловно отличить старый пакет
  без времени от нового взвешивания. Это ограничение протокола, не постоянного соединения.
- При перерегистрации сканера возможен короткий пропуск пакетов; шкала должна
  успеть передать стабильный пакет. Без пакета программа не выдумывает вес.
- Последний сохранённый вес не имеет срока годности: потребитель персонализации
  обязан учитывать timestamp. Усилие двигателя не корректируется.
- Импеданс сохраняется опционально. Жир, вода и медицинские показатели не вычисляются.
- При выключенном поиске адаптер не опрашивается; `bluetoothAvailable=false`
  означает отсутствие подтверждённой доступности, а не доказанную неисправность.
