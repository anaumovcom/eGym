# Выполнение на каждую сторону

## Настройка и выполнение

- В конструкторе флажок **«На каждую сторону»** (`perSide`) сохраняется для выбранного упражнения. Числа в плане не удваиваются: **1×10 = 10 повторов левой + 10 правой**, то есть одна пара и 20 повторов всего.
- Порядок: левая → правая → следующая пара. При смене стороны требуется явное подтверждение **«Начать правую сторону»**. Автоматического запуска упражнения или тренажёра нет, даже при нулевом таймере перехода.
- Заданный отдых начинается после пары, а не между левой и правой сторонами.
- В режиме **«На время»** длительность задаётся на каждую сторону: 1×30 сек = 30 сек слева + 30 сек справа, всего 60 сек. Секунды не включаются в общий счётчик повторов тренировки.

## Результаты и хранение

- Повторы суммируются по фактически выполненным сторонам; пары считаются отдельно. Только левая сторона с 10 повторами — это 10 повторов, но 0 завершённых пар. Для завершённой пары 1×10 итог: **1 из 1 пар · 2 из 2 сторон**, 20 повторов.
- В плане конструктора и `working_sets` учитываются пары; `working_reps` хранит общее число повторов, а `lastResult.repsPerSet` — среднее на одну сторону. В runtime `setNumber` и `targetSets` остаются физическими подходами по сторонам; `side` и `roundNumber` сохраняются в `machineMetrics`. `plannedTotal` — сумма целей всего развёрнутого плана, включая ещё не выполненные стороны.
- [Миграция 0011](../../backend/alembic/versions/20261016_0011_runtime_per_side_plan.py) идёт после [0010](../../backend/alembic/versions/20261016_0010_exercise_load_direction.py) и добавляет в `exercise_sessions` поля `per_side` (по умолчанию `false`) и `planned_total` (допускает `NULL`). API использует `perSide` и `plannedTotal`.
- Обратная совместимость: старые планы без флажка работают как раньше (`perSide=false`); старые результаты с метками сторон распознаются по `machineMetrics`, без меток сохраняют обычный подсчёт подходов. Отсутствие новых полей в запросе обновления не стирает уже сохранённые метаданные.

См. [описание экрана](exercise-session.md) и [проверки хранения и совместимости](../../backend/app/tests/test_runtime_per_side.py).

## Точечное применение к локальной БД — 2026-10-16

- Настройки приложения и Alembic указывают на [рабочую БД](../../backend/egym_local.db); `sqlalchemy.url` в Alembic не переопределён. До ремонта `alembic_version` содержала `20260928_0006`, хотя таблицы 0007/0008 и `exercise_calibrations.start_point` из 0009 уже существовали. Полная эквивалентность поздним миграциям **не подтверждена**: например, в `coach_jobs` отсутствует `failures` из 0007, а `exercise_calibrations.load_direction` из 0010 отсутствует. Причина исторического расхождения не установлена; `create_all` — возможное, но не доказанное объяснение.
- Поэтому обычное обновление до head останавливается на уже существующей `coach_preferences`. Выполнять `stamp head` нельзя: это скроет реальные пропуски схемы. Версия оставлена `20260928_0006`; согласование истории миграций — отдельная задача.
- Использован [DB-only скрипт ремонта](../../backend/scripts/repair_runtime_per_side.py): по умолчанию read-only; для записи нужны `--database`, `--apply` и `--backup`. Проверяются совпадение явного пути с эффективным URL, существование и целостность резервной копии. Использована [ранее созданная SQLite-копия](../../backend/egym_local.db.bak-before-0011-20261016-195348); восстановления из неё не было.
- Скрипт открывает существующий файл без возможности создания, получает короткую `BEGIN IMMEDIATE` с таймаутом блокировки 1 секунда и вызывает **только** `upgrade()` ревизии 0011 через `MigrationContext.configure(connection)` и `Operations.context(...)`. Нет запуска цепочки миграций, stamp, bootstrap приложения, HTTP или hardware lifecycle. При ошибке проверки DDL откатывается явной транзакцией.
- [0011](../../backend/alembic/versions/20261016_0011_runtime_per_side_plan.py) проверяет совместимость уже существующих новых колонок до DDL и добавляет только отсутствующие. В рабочей БД добавлены ровно `per_side BOOLEAN NOT NULL DEFAULT 0` и `planned_total FLOAT NULL`. Ни 0010, ни другие отсутствующие элементы схемы не применялись.
- Внутри транзакции до/после совпали счётчики и SHA-256 исходных значений всех 34 таблиц, исходные колонки и остальные объекты схемы. Сохранены 20 `exercise_sessions`, 39 `set_results`, 8 `workout_sessions`, 78 событий усталости, 163 калибровочных запуска и 93 профиля машины. Новые поля старых сессий получили `false`/`NULL`; старые значения не переписывались. Хеши относятся к моменту транзакции, не к более ранней копии: работающий процесс может самостоятельно менять данные между проверками.
- После commit новое read-only соединение подтвердило отсутствие пропусков 0011, прежнюю версию, `PRAGMA quick_check = ok` и успешный ORM SELECT всех 20 `ExerciseSession`. Проверены именно доступность схемы и чтение ORM, не полный сценарий тренировки/API.
- [Изолированные тесты](../../backend/scripts/tests/test_repair_runtime_per_side.py): 6 успешных проверок — обе колонки отсутствуют, каждая по отдельности, обе уже есть, несовместимый тип, откат DDL при ошибке ORM. Линтер прошёл. Оборудование и сервисы не останавливались/не перезапускались; моторных запросов не выполнялось.
