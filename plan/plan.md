# План разработки Forma

Документ описывает поэтапную разработку полноценной версии Forma на основе документации из `docs`.

Ключевое решение: сначала разрабатывается весь фронтенд на моках, чтобы быстро проверить интерфейс, сценарии, 4K-компоновку и сенсорное управление. После согласования фронта подключается полноценный Python-бэкенд, затем оборудование, безопасность, интеграция и релиз.

Это не MVP-план: каждый этап должен закрывать полный объём своего слоя, включая состояния ошибок, пустые состояния, модальные окна, панели, безопасность и тесты.

---

## Базовый стек

### Frontend

* React + TypeScript.
* Vite.
* TailwindCSS.
* shadcn/ui + Radix UI для доступных базовых компонентов.
* `lucide-react` как основная иконографика.
* `@phosphor-icons/react` как дополнительная библиотека для более выразительных фитнес- и системных иконок.
* `react-icons` только если в первых двух библиотеках нет нужной пиктограммы.
* React Router.
* TanStack Query.
* Zustand для локального UI-состояния и live-состояний тренировки.
* MSW для мокового API.
* Storybook для компонентов и экранных состояний.
* React Hook Form + Zod для форм.
* Recharts или Apache ECharts для графиков прогресса.
* Framer Motion для аккуратных переходов, оверлеев и live-состояний.
* Vitest + Testing Library + Playwright.

### Backend

* Python 3.12+.
* FastAPI.
* Pydantic v2.
* SQLAlchemy 2.x + Alembic.
* PostgreSQL.
* Redis для кэша, очередей и live-состояний.
* Celery / RQ / Arq для фоновых задач.
* WebSocket или SSE для live-статусов тренажёра и выполнения подхода.
* MinIO или совместимое S3-хранилище для фото прогресса и медиа.
* pytest, Ruff, mypy/pyright.
* OpenAPI как единый контракт между фронтом и бэкендом.

### Hardware / realtime

* Отдельный слой интеграции с приводами, ШВП, безопасностью и калибровкой.
* Никакие команды движения не выполняются напрямую из UI: только через серверный safety-gate.
* `СТОП` и аварийные блокировки имеют приоритет над любым сценарием.

## Порядок разработки

1. Сначала полностью собрать frontend shell и все ключевые экраны на моках.
2. Проверить сценарии руками на 4K/тач-ориентированной компоновке.
3. Исправить спорные интерфейсные решения до подключения реального backend.
4. Зафиксировать OpenAPI-контракты по фактическим потребностям фронта.
5. Реализовать backend без изменения уже согласованного UX.
6. Подключить realtime и оборудование только после готовности safety-модели.
7. Провести полную интеграционную проверку всех маршрутов.

## Общие правила для всех этапов

* Не возвращать отдельный экран предстартовой проверки: все проверки перед упражнением живут на экране `Настройка упражнения`.
* `Проверка необходимости фото прогресса` — логический шаг, не отдельный экран.
* Компоненты из `docs/common/ui-components.md` должны быть переиспользуемыми, а не копироваться в каждый экран.
* Модальные окна, правые панели, оверлеи и уведомления должны соответствовать `docs/common/modals-panels-overlays.md`.
* Усталость мышц считается через `fatigueScore` и пересчитывается по фактическому времени, включая время выключенного сервера.
* Все опасные действия требуют подтверждения или блокирующего состояния.
* `СТОП` всегда доступен поверх любого UI.
* Все экраны проектируются под премиальный тёмный 4K-интерфейс.

## Definition of Done для этапа

Этап считается завершённым, если:

* реализованы все экраны, компоненты или backend-модули, заявленные в этапе;
* покрыты пустые, ошибочные, загрузочные и блокирующие состояния;
* сценарии проходят через UI или API без ручных обходов;
* есть тесты для критической логики;
* обновлены моковые данные или контракты;
* скриншоты из `docs` использованы как визуальные ориентиры;
* нет временных решений, которые противоречат полной версии продукта.
